# Heavy Ads Tool

Test bed and tools for the **heavy ad detection script**: the small script that reports when Chrome removes an ad for using too many resources.

Chrome unloads an ad frame that uses more than **4 MB of network**, or more than **15 s of main-thread CPU in any 30 s window**, or more than
**60 s of CPU in total**. It raises an `intervention` report (`HeavyAdIntervention`) through the Reporting API. The script listens for that report and
fires a pixel. This repo lets you prove that, for each kind of creative.

Desktop Chrome only (other browsers have no such intervention). Needs Node.js for the local test bed. No `npm install` is needed.

## What are you testing?

| Creative type | Where the creative runs | Test page | Result when tested |
|---|---|---|---|
| **Simple banner** | Same-origin frame (like a GAM friendly iframe) | `/creative?type=friendly` | Removed after about 17.5 s, one pixel |
| **Cross-origin iframe banner** | Creative served from another origin, in an iframe nested inside the ad frame | `/creative?type=cross` | Removed after about 17.8 s, one pixel |
| **SafeFrame-like banner** | Cross-origin and sandboxed (document origin `null`, storage blocked) | `/creative?type=sandbox` | Removed after about 17.5 s, one pixel |
| **VPAID video (IBV)** | VPAID code run by Google's IMA SDK in its own cross-origin iframe | `/vpaid` | Removed after about 2 s (network flood), one beacon |
| **Your GAM creative** | A creative served by your own Google Ad Manager ad unit | `/gam?unit=...` | Not run here (needs your ad unit and line item) |
| **Any live page** | Same-origin ad frames on any site, via the DevTools panel | `/panel`, `install.html` | Run on a live news site, one real beacon seen in DevTools |

Not tested: a real Google SafeFrame (the sandboxed cross-origin frame is the stand-in), and creatives served from your own GAM account.
The banner pages also accept **any creative HTML** that you paste or load from a file.

## Quick start

```
node local-test-bed/server.js
```

Open `http://localhost:8770/`. The index page lists every creative type above with a **Test** button. On each test page:

1. Wait for the page to load its ad. Keep the tab in front and **do not click inside the ad** (a click exempts it from the intervention).
2. Click **Start**. The creative burns CPU or floods the network on purpose.
3. After about 2 to 60 s Chrome removes the ad. The page shows **PASS** (exactly one pixel or beacon), FAIL, or INFO, plus a timeline.

The verdict names the creative type that was tested and which path sent the pixel: the observer callback, or the `pagehide` drain (`takeRecords()`),
which catches a report that arrives too late for the callback.

## The script under test

```js
(function () {
var PIXEL = "HEAVY_AD_PIXEL";

function send(reports) {
    for (var i = 0; i < reports.length; i++) {
        try {
            var body = reports[i].body;
            if (!body || body.id !== "HeavyAdIntervention") { continue; }
            var sep = "&";
            navigator.sendBeacon(PIXEL + sep + "rd=" + encodeURIComponent(JSON.stringify({
                message: body.message, sourceFile: body.sourceFile,
                lineNumber: body.lineNumber, columnNumber: body.columnNumber
            })));
        } catch (e) {}
    }
}
try {
    var observer = new ReportingObserver(send, { types: ["intervention"], buffered: true });
    observer.observe();
    window.addEventListener("pagehide", function () { send(observer.takeRecords()); });
} catch (e) {}
})();
```

Your pixel URL must already contain a `?`, because the script appends `&rd=...`.

## Using each test

### Banner creatives (simple, cross-origin, SafeFrame-like)
Open `/creative?type=friendly`, `?type=cross` or `?type=sandbox`. Leave the box empty to load `heavy-creative.html`, or paste any creative HTML
(or choose a file). Tick **add the sample script** and **add the CPU burn** to arm and stress your own creative, or untick them to see whether your
creative gets removed on its own. The pixel goes to the local server, which logs it.

### VPAID video (IBV)
Open `/vpaid`. It plays a heavy VPAID VAST creative with the IMA SDK (a short CPU burn plus repeated fetches of a 6 MB sample video, to pass the
4 MB network limit). Options: add the sample script and a reporter, capture or really send the beacon, how many files to fetch (the original fixture
used 50, the page defaults to 10), and deliver the VPAID code as a `data:` URI or from the local server (use this if IMA rejects the `data:` URI).
The VAST XML is available from the link on the page.

### Your own GAM creative
1. Put `heavy-creative.html` in a GAM **Custom HTML** creative (real pixel instead of `HEAVY_AD_PIXEL`) on a line item that serves to a test ad unit.
2. Open `http://localhost:8770/gam?unit=/NETWORK_CODE/AD_UNIT_PATH&size=300x250`.
3. Watch your pixel in DevTools > Network (Preserve log, filter on your pixel host). A `ping` row with an `rd` parameter is the proof.

### A live page (the panel)
1. Open the page in desktop Chrome, let ads load, and turn **device emulation off** (Ctrl+Shift+M in DevTools).
2. Open `install.html`, click **Copy tool code**, paste it into the DevTools Console and press Enter (type `allow pasting` first if Chrome asks).
3. Pick an ad frame in the panel, choose **Capture only** (nothing sent) or **Send a real beacon**, and click **Start test**.

The panel can only drive same-origin frames. Cross-origin frames are listed greyed out.

## What the verdicts mean

| Verdict | Meaning |
|---|---|
| PASS | Chrome removed the frame and exactly one beacon was sent. The text says which path sent it. |
| FAIL: more than one beacon | The script sent duplicates. |
| FAIL: removed, no beacon | Chrome removed the frame but the script did not send. A real bug to look at. |
| FAIL: nothing happened | The frame was probably not tagged as an ad, the tab was hidden or unfocused, the ad was clicked, the creative was not heavy enough, or the intervention is disabled in this Chrome. |
| INFO: page replaced the frame | The site refreshed the ad before Chrome acted. No beacon is correct. Retry. |

## Things that commonly go wrong

- **Device emulation on**: the page serves a mobile layout with different ad slots, and DevTools can turn emulation back on when you open it.
- **Ad refresh**: many sites replace ad frames every few seconds. The panel disables `googletag.pubads().refresh()` for the page view by default.
- **Frame not reachable**: the panel only works on same-origin frames. Cross-origin creatives carry their own script (use the creative pages or `heavy-creative.html`).
- **Chrome only**: other browsers have no heavy ad intervention.
- **Noisy thresholds**: Chrome adds random noise to the limits, so removal usually happens after 15 to 20 s of CPU but can take up to about 60 s.
- **Network limit uses real downloads**: the VPAID test fetches a Google sample video. The downloads stop when Chrome removes the frame.

## What the tools change

- `heavy-creative.html` and the VPAID creative: run the sample script and a load generator inside their own frame, nothing else.
- The panel: inside the chosen frame only, replaces `navigator.sendBeacon` with a wrapper (records the call, sends only in real mode), adds diagnostic
  listeners, installs the sample script and starts the load. On the page it optionally replaces `googletag.pubads().refresh` with a no-op.
  Close the panel with the x button, or reload the page, to remove everything.
- A real beacon is sent only when you choose **Send a real beacon**, and only to the pixel URL you set.
